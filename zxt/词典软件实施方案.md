> 项目代号临时用 **LexiPop**，可随时改名
> 状态：**已定稿并开工**，决策记录见下方

## 决策记录（已确认，2026-10-27）

| 决策项 | 结论 | 理由摘要 |
|---|---|---|
| 技术栈 | **C# + .NET 10 + WPF**，单进程 | 40–90 MB 常驻；Rust 版只省 ~30 MB 但代码量 3–5 倍、调试成本 5–10 倍 |

| 划词交互 | 选中文本 → 浮出**无激活小按钮** → 点击原地展开卡片 | 先取词再弹窗，避免失焦丢选区 |
| 取词链路 | UIA → 模拟 Ctrl+C 读剪贴板 → OCR（手动） | Windows 无统一取词 API |

## 0. 一句话结论

**可行，但要把"划词取词"当作核心风险来设计。**

五条需求中，内存、响应、快捷键、发音都是成熟的工程问题，有确定解；只有"划词翻译"在 Windows 上没有全局通用的取词接口，必须用**三级降级策略**（UI Automation → 剪贴板模拟 → 屏幕 OCR）兜住不同应用。这不是技术不可行，而是"不可能用一种方法覆盖所有窗口"，方案必须按"能取到"和"取不到"两条路径来设计交互。

## 2. 技术选型

### 2.1 候选方案对比

| 方案 | 常驻内存 | 启动速度 | 取词/热键能力 | 开发效率 | 结论 |
|---|---|---|---|---|---|
| **C# + .NET 10 + WPF(Windows Presentation Foundation)** | 40–90 MB | 快 | 原生 Win32 互操作，最顺 | 高 | ✅ **主选** |
| C# + WinUI 3 | 40–70 MB | 中 | 可以，但打包与互操作更绕 | 中 | 备选 |
| Rust + Tauri + WebView2 | 100–150 MB | 中 | 需在 Rust 侧手写 | 中高 | ❌ 内存不达标 |
| C++ + Qt | 30–60 MB | 快 | 原生 | 低 | ❌ 开发成本过高 |
| Electron | 200–400 MB | 慢 | 需 Node 原生模块 | 高 | ❌ 直接违背需求 |
| Python + PyQt | 150–250 MB | 慢 | 一般 | 高 | ❌ 打包体积与内存双输 |

### 2.2 为什么选 WPF

1. **单进程模型**，没有 Chromium 那种多进程常驻开销。WPF 的空窗口工作集实测在 40–60 MB 区间，是本项目里唯一能同时满足"内存小"和"开发快"的组合。
2. **Win32 互操作几乎零成本**：全局热键、全局钩子、UI Automation、剪贴板、`SendInput` 都有现成的 P/Invoke 路径。
3. **生态成熟**：托盘图标、无边框窗口、Mica 背景、本地化都有大量现成实现。
4. .NET 10 是当前长期支持版本（Long Term Support，LTS），运行时稳定。

唯一要注意的是 **WPF 不支持 NativeAOT（Ahead-of-Time 编译）**，所以启动优化只能靠 ReadyToRun 和预热，不能靠 AOT。这不影响可行性。

### 2.3 为什么不用 Tauri

Tauri 常被推荐给"轻量桌面应用"，但它的轻量是相对 Electron 的。实际运行时是"Rust 主进程 + WebView2 多进程（browser / renderer / GPU / utility）"，一个空白 WebView2 页面常驻就有 60–100 MB。对本项目来说，"内存占用小"是硬指标，Tauri 在这个指标上直接出局。

**结论：C# + .NET 10 + WPF，单进程，不引入任何 Web 渲染层。**

## 4. 关键技术设计

### 4.1 全局热键与毫秒级唤出

**热键注册**用 Win32 的 `RegisterHotKey`，在 `HwndSource` 的 `WM_HOTKEY` 消息里处理：

```csharp
[DllImport("user32.dll")]
static extern bool RegisterHotKey(IntPtr hWnd, int id, uint fsModifiers, uint vk);

const uint MOD_CTRL = 0x0002, MOD_ALT = 0x0001, MOD_SHIFT = 0x0004;
const int WM_HOTKEY = 0x0312;

// 例如 Ctrl+Alt+D
RegisterHotKey(hwnd, 1, MOD_CTRL | MOD_ALT, 0x44 /* D */);
```

**推荐热键**：`Ctrl+Alt+D`（主唤出）、`Ctrl+Alt+S`（划词翻译）、`Alt+\``（另一种习惯）。
**不要用 `Alt+Space`**，它被系统窗口菜单占用，`RegisterHotKey` 会失败。

**唤出速度优化清单**（目标：热键按下到窗口可交互 < 80ms）：

1. **窗口预先创建**，开机后立刻 `new MainWindow()` 然后 `Hide()`，保持 HWND 存活。唤出时只做 `Show()`，不做 `new Window()`——省掉 XAML 解析（约 150–300ms）。
2. **预渲染一次**：启动时以 `Opacity=0` 显示 1 帧再隐藏，触发字体加载和首次布局，避免"第一次唤出卡顿"。
3. **输入框预聚焦**：`Show()` 后立即 `Activate()` + `textBox.Focus()`，并预选中上次查询文本，方便直接覆盖输入。
4. **置前技巧**：Windows 有前台窗口锁定策略，必要时用 `AttachThreadInput` 或临时 `Topmost=true` 保证窗口真的浮到最前。
5. **不要用启动动画**。WPF 的 `Storyboard` 和模糊/阴影效果会走软件渲染层，是唤出延迟和数据内存的主要来源。Win11 的 Mica 背景用 `DwmSetWindowAttribute` 设置，开销可忽略。
6. **关闭后台线程池预热**：启动时发一个空查询走完管线，把 SQLite 连接、HTTP 连接池、TTS 合成器都初始化好。

### 4.2 划词取词：三级策略（核心难点）

Windows 没有任何一个 API 能"读取任意窗口里的选中文本"，所以必须按可靠性从高到低降级：

#### 第一级：UI Automation（UIA）

Windows 无障碍 API，直接读取控件的文本选区，**不碰剪贴板**，最干净。

```csharp
var focused = AutomationElement.FocusedElement;
if (focused.TryGetCurrentPattern(TextPattern.Pattern, out var p))
{
    var tp = (TextPattern)p;
    var ranges = tp.GetSelection();
    if (ranges.Length > 0)  // 注意：GetSelection() 返回 1 个空 range 表示无选区
    {
        string text = ranges[0].GetText(500);
    }
}
```

- **覆盖**：Chrome、Edge、记事本、Word、VS Code、Windows Terminal、大部分现代应用。
- **盲区**：游戏（DirectX 渲染）、Adobe Reader、部分 Java 应用、某些自绘控件、管理员权限进程下的普通权限程序。
- **前提**：浏览器需要在设置里开启"辅助功能"暴露（Chrome/Edge 默认已开）。

#### 第二级：模拟 Ctrl+C + 读剪贴板

UIA 失败时的兜底，也是最通用的方法。

```
1. 记录 GetClipboardSequenceNumber() 当前值
2. SendInput 发送 Ctrl+C
3. 轮询等待剪贴板序列号变化（上限 300ms，间隔 20ms）
4. 读取文本内容
5. 恢复用户原来的剪贴板（保存过原文本的情况下）
```

坑位：
- 剪贴板被其他程序占用时 `OpenClipboard` 会失败，必须带重试（3 次，间隔 50ms）。
- 恢复剪贴板不要"清空再写回"，很多程序持有格式引用会崩。做法是**只把文本写回**，接受丢失富文本格式。
- 有些程序 Ctrl+C 后剪贴板里是 HTML/RTF，要优先取 `CF_UNICODETEXT`。
- 对终端模拟器（如某些 SSH 客户端）Ctrl+C 是中断信号，会误伤——所以这个方案**只在热键触发时执行，绝不自动执行**。

#### 第三级：屏幕 OCR（Optical Character Recognition，光学字符识别）

针对图片、扫描版 PDF、游戏、任何 UIA 和剪贴板都拿不到的场景。
用 Windows 自带的 `Windows.Media.Ocr`（WinRT API，离线、免费、中英文都支持）：

```
截取鼠标附近区域或用户框选区域 → SoftwareBitmap → OcrEngine.RecognizeAsync → 文本
```

- 延迟 300–800ms，明显比前两级慢，所以**只作为用户显式选择**（右键菜单"OCR 识别这片区域"），不做默认链路。
- 识别后用 `Levenshtein` 距离或 `SymSpell` 做一次拼写纠错再查词典。

#### 触发方式设计：选区浮窗按钮（已定方案）

```
鼠标拖选松开
   │
   ├─ 全局鼠标钩子 WH_MOUSE_LL 检测左键抬起，且拖拽距离 > 3px
   │
   ├─ 延迟 30~50ms（等目标应用的 UIA 选区更新完）
   │
   ├─ 取词：UIA TextPattern → 失败则模拟 Ctrl+C 读剪贴板
   │        （**先拿到文本并缓存**，再弹按钮）
   │
   ├─ 取矩形：TextPatternRange.GetBoundingRectangles() 换算屏幕坐标
   │        （多显示器 + DPI 缩放都要换算）
   │
   └─ 浮出小按钮（WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST）
              │
              └─ 点击 → **原地展开**成 320×420 的结果卡片（不新建窗口）
```

**四个必须遵守的约束**：

1. **先取文本再弹窗。** 按钮一出现，点击会让原窗口失焦，浏览器/Office 的选区会消失，之后再读 UIA 就是空的。文本和矩形必须在弹出前缓存。
2. **浮窗不抢焦点。** 用 `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TOPMOST` 创建，否则会进 `Alt+Tab`、让原窗口闪烁、甚至打断输入。
3. **事件驱动，不轮询。** 只在左键抬起时检查一次选区，绝不后台轮询 UIA（会持续吃 CPU）。
4. **可编辑控件要过滤。** `ControlType == Edit` 内拖选会高频误触，默认跳过。

**误触控制**：浮窗按钮默认开启，但提供"仅单词长度 1–3 时触发"和"整体关闭"两个开关；热键 `Ctrl+Alt+S` 始终可用作不依赖浮窗的兜底入口。

| 方式 | 默认 | 说明 |
|---|---|---|
| 选中后浮出小按钮 | ✅ 开启 | 主交互 |
| 选中后按热键 `Ctrl+Alt+S` | ✅ 开启 | 兜底，浮窗失效时仍可用 |
| 鼠标中键 / 侧键触发 | ❌ 可选 | 部分用户习惯 |
| 后台轮询选区 | ❌ 永不 | 性能不可接受 |

### 4.3 查询与翻译管线

输入归一化后，按类型走不同路径，**本地结果先出，在线结果异步补**：

```
输入
 ├─ 单词 → ① 本地 ECDICT 精确查 → 即刻渲染（<30ms）
 │        ② 命中则同时异步拉 LLM 补充"语境例句/辨析"（可选）
 │        ③ 未命中 → 拼写纠正 → 仍无则走翻译
 └─ 句子 → ① 查翻译缓存（SQLite + 内容哈希）
           ② 未命中 → LLM 流式翻译，逐字渲染
           ③ 同时可并发传统引擎做对照（可选开关）
```

**翻译准确性的三层保障**：

1. **本地词典兜底单词释义**：牛津 MDX 词库（构建期解析为 SQLite，只保留音标、词性、释义、例句等结构化字段），单词查询 <10ms、零网络请求。
2. **LLM(Large Language Model) 做句子翻译**：`deepseek-flash`，非思考模式，提示词约束"只输出译文、保留 Markdown 结构、术语表一致、不解释"。这是目前长句准确率最高的方案。
3. **缓存**：同句重复查询直接命中，省请求也省延迟。

**成本测算（2026-10 官网价，`deepseek-flash`）**：

| 项目 | 低谷 | 高峰 |
|---|---|---|
| 输入（缓存未命中） | $0.15 / 1M | $0.30 / 1M |
| 输入（缓存命中） | $0.003 / 1M | $0.006 / 1M |
| 输出 | $0.60 / 1M | $1.20 / 1M |

按高峰价、单句 200 输入 + 130 输出 token 估算：**约 ¥0.0016/句**。轻度使用（每天 30 句）月成本约 ¥1.5，中度（每天 100 句）约 ¥5，重度（每天 300 句）约 ¥15。单词查本地词典不消耗 API，重复句子走缓存也不消耗。

**接口抽象**：`ITranslator` provider 接口，默认 DeepSeek，可切换免费接口或本地 Ollama（后者会额外占用 3 GB 级内存，默认关闭）。

**为什么不用"多引擎投票"**：对个人项目来说，多引擎对照是展示层面的花活，不提升准确率，反而增加延迟和 key 管理成本。留一个"显示第二引擎译文"的开关即可。

### 4.4 发音

音源按质量与可靠性排序，带本地缓存：

| 优先级 | 音源 | 延迟 | 适用 | 说明 |
|---|---|---|---|---|
| 1 | **牛津 mdd 真人音**（构建期提取） | ~0ms | 单词 | 真人录音，质量最高，完全本地 |
| 2 | 在线神经网络 TTS(Text-to-Speech) | 200–500ms | 长句 | Edge 神经音色，自然度最好 |
| 3 | 在线真人音（有道 `dictvoice`） | 100–300ms | 单词兜底 | 英式/美式两版 |
| 4 | 本地 SAPI(Speech Application Programming Interface) | <100ms | 离线兜底 | 音质机械，但完全离线 |

**牛津 mdd 是最大的红利**：牛津 MDX 通常附带 `mdd` 语音库（MP3 打包），构建期把音频提取到本地目录，单词发音零延迟、零网络请求，且是真人录音。这一项优先级最高。

**缓存策略**：TTS 合成结果落盘到 `%LOCALAPPDATA%\LexiPop\audio\<sha1>.mp3`，第二次播放零延迟，总量上限 200 MB，LRU(Least Recently Used) 淘汰。

**一个必须提前知道的坑**：中文版 Windows 默认**没有安装英语语音**，`System.Speech` 里 `GetInstalledVoices()` 只能拿到中文语音。首次使用离线发音时必须引导用户"设置 → 时间和语言 → 语言和区域 → 添加语言 → English (United States) → 勾选语音"，并在代码里做检测和提示。否则用户会以为发音功能坏了。

### 4.5 内存与性能预算

| 场景 | 目标内存 | 目标延迟 |
|---|---|---|
| 冷启动到托盘可用 | 45–60 MB | < 1.5 s |
| 常驻空闲（隐藏窗口） | 40–55 MB | — |
| 热键唤出瞬间 | +5 MB | < 80 ms |
| 本地查词渲染完成 | 70–90 MB | < 40 ms |
| 流式翻译首字出现 | 75–95 MB | < 1 s（受网络影响） |
| OCR 识别 | +30 MB（临时） | 300–800 ms |

对照：同功能的 Electron 实现常驻 250 MB 以上，Tauri 约 120 MB。**40–90 MB 是 WPF 正常水平，不需要特殊手段就能达到**；如果追求 20 MB 级别，才需要换 Rust。

**内存优化清单**：

1. **框架依赖部署**（需用户装 .NET 10 Desktop Runtime），共享框架映射，比自包含部署省内存和磁盘。
2. 词典数据 **SQLite 按需查询**，用 `mmap` 打开，绝不全量读进内存。
3. 词条对象用 `WeakReference` 做二级缓存，让 GC 在压力下能回收。
4. 空闲 5 分钟后调用 `EmptyWorkingSet` 压工作集（注意：会造成下次访问 page fault 稍慢，所以只在空闲时做）。
5. 图片资源用 `BitmapCacheOption.OnLoad` 加载后立即释放文件句柄，避免内存泄漏。
6. 不用 `Effect`（阴影、模糊），它们会创建软件渲染位图。

## 5. 数据与存储设计

```
%LOCALAPPDATA%\LexiPop\
├─ dict.db          # ECDICT 精简版，SQLite，只读
├─ cache.db         # 翻译缓存 + 生词本 + 历史（读写）
├─ audio\           # TTS 音频缓存，LRU
├─ settings.json    # 配置：热键、引擎、UI 主题
```

**核心表**：

```sql
-- 词典（只读，构建期由牛津 MDX 解析生成）
CREATE TABLE dict (
  word      TEXT PRIMARY KEY COLLATE NOCASE,
  phonetic  TEXT,      -- 音标
  senses    TEXT,      -- JSON: [{pos, def, examples[]}]
  audio_uk  TEXT,      -- mdd 提取的英式音频文件名
  audio_us  TEXT,      -- 美式音频
  freq      INTEGER    -- 词频/难度，用于排序
);
CREATE INDEX idx_word_prefix ON dict(word COLLATE NOCASE);

-- 翻译缓存（读写）
CREATE TABLE cache (
  hash      TEXT PRIMARY KEY,  -- sha256(文本+引擎+语言对)
  source    TEXT, target TEXT,
  engine    TEXT, created_at INTEGER,
  hits      INTEGER DEFAULT 0
);

-- 生词本
CREATE TABLE vocab (
  id INTEGER PRIMARY KEY, word TEXT UNIQUE,
  note TEXT, created_at INTEGER, review_at INTEGER
);
```

## 8. 风险清单

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| UIA 在目标应用失效 | 高 | 取词失败 | 三级降级 + 用户手动粘贴兜底 |
| 全局热键被其他软件占用 | 中 | 唤不出 | 注册失败时提示并引导换键 |
| 在线翻译/TTS 接口变更或收费 | 中 | 功能降级 | 接口抽象成 provider，可切换；本地 SAPI 兜底 |
| 中文系统缺英语语音 | 高 | 离线发音无声 | 启动检测 + 引导安装语言包 |
| 杀软误报全局钩子 | 低 | 安装受阻 | 优先 UIA 而非键盘钩子；只签必要的可执行文件 |
| 剪贴板污染用户数据 | 中 | 体验差 | 只在热键触发时取词；取完恢复纯文本 |
| LLM API 成本 | 低 | 费用 | 缓存 + 单词走本地词典，句子才调 API；单次翻译成本约几分钱/千字 |
| 管理员权限窗口取词失败 | 高 | 少数场景 | 文档说明；可选"以管理员运行"模式 |

## 9. 决策状态

**已确认（2026-10-27）**：技术栈用 C# + .NET 10 + WPF；翻译后端用 DeepSeek `deepseek-flash`；词典数据用牛津 MDX 构建本地 SQLite；划词交互用选区浮窗按钮。详见文首决策记录。

**仍需补齐的实施输入**：

1. **牛津词典文件**：需要 `.mdx` 词库和配套 `.mdd` 音频库的本地路径（个人自用，自行把握版权）。
2. **DeepSeek API Key**：在 platform.deepseek.com 申请，密钥只存本地配置，不入库、不进日志。
3. **默认热键**：暂定 `Ctrl+Alt+D` 唤出、`Ctrl+Alt+S` 划词翻译，冲突时可改。

## 10. 附：三个"能否更快更小"的极端选项

如果上面方案的 40–90 MB 仍不满足：

- **Rust + `windows-rs` + Direct2D 自绘**：常驻可压到 15–25 MB，启动 < 200ms。代价是所有 UI 和 XAML 都要手写，开发周期翻 3 倍。
- **Go + 轻量 GUI（如 `wails` 的 native 模式 / `walk`）**：约 25–40 MB，开发效率高于 Rust，但 Windows 生态和 UIA 绑定较弱。
- **放弃独立进程**：做成"PowerToys 插件"或"Everything 式驱动"，共享宿主内存。但会失去独立启动和自更新能力，不推荐。

对个人项目，**WPF 方案是"内存、速度、开发成本"三角的最优解**，没有理由为了压 20MB 而牺牲一个月工期。
